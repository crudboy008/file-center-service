# ADR-002 V0.1.0 延迟接入 RAG 并冻结合同

- 日期：2026-09-03
- 状态：一期范围已由用户确认；本文契约细节 `DRAFT_FOR_USER_REVIEW / NOT_APPROVED_FOR_IMPLEMENTATION`
- 适用版本：V0.1.0

## 1. 背景

V0.1.0 的交付目标是 Java 文件管理，Python RAG/Agent 不真实接入；同时，后续 RAG 入库不能等实现时再临时定义消息和文件引用，否则 Java 的 Object Key、SHA-256 和数据模型可能需要返工。

用户进一步确认：Java 文件修改必须在未来通过 MQ 让 RAG 得知当前状态；正文不在线编辑，只允许上传完整文件替换；当前版本仍不接 MQ，只先固定双方合同。现有 `document_submitted v2` 使用 `document_id=reference_id` 且按 `document_id` 分组，替换会生成新 `reference_id`，因此它不能单独表达“同一逻辑 `file_id` 的旧文档已被新文档替代”，也不能表达启停和删除状态。

现有 RAG 参考实现已经对 Topic、Envelope、JSON 字段和 MinIO 引用方式形成静态兼容基线。外部设计输入 `compatibility-audit.md` 第 4～6 节记录了这些约束；同文第 7～9 节明确当前 Java 工程未创建、完整端到端联通未执行。

## 2. 决策

V0.1.0 只交付跨语言契约及静态契约验证，不启动或模拟 RAG 运行链路。

### 2.1 保留 Java → RAG 入库兼容合同

| 项目 | 固定值/规则 |
|---|---|
| Topic | `card_rag_doc_intake` |
| Topic 类型 | FIFO |
| Tag | `document_submitted` |
| Key | 恰好一个，等于 `operation_id` |
| MessageGroup | 等于 `document_id` |
| Body | UTF-8 JSON，`schema_version=2.0` |

Body 至少按字段级契约冻结：`schema_version`、`event_type`、`operation_id`、`document_id`、`file_ref`、`expected_content_sha256`、`knowledge_domain`、`business_document_class`、`access_scopes`、`submitted_by`、`submitted_at`。精确长度、格式、额外字段拒绝规则和 RFC 3339 时间约束由 LLD 的 JSON Schema 定义。

`document_submitted v2` 是严格兼容基线，不在原 Schema 中直接增加 `file_id/status` 等字段。逻辑文件状态由 2.5 的新 Tag 和新 Schema 承载；未来切流或双读策略必须另行评审，V0.1.0 不运行双发。

### 2.2 冻结 RAG → Java 接纳结果目标合同

当前 Python 的 intake 用例在进程内能够区分首次接纳、业务拒绝和同一 `operation_id` 不同 payload 的冲突，但现有结果 Outbox 只发送最终 `document_ingestion_result`，无法把“尚未创建任务即被拒绝/冲突”可靠回传给 Java。因此冻结一个新增的目标事件：

| 项目 | 固定值/规则 |
|---|---|
| Topic | `card_rag_document_result`，与最终结果使用同一 Topic |
| Topic 类型 | FIFO |
| Tag | `document_ingestion_acceptance` |
| Key | 恰好一个，等于 `operation_id` |
| MessageGroup | 等于 `operation_id` |
| Body | UTF-8 严格 JSON Object，`schema_version=1.0` |
| 状态分支 | 严格三分支：`ACCEPTED`、`REJECTED`、`CONFLICT` |

公共字段为 `schema_version`、`event_type=document_ingestion_acceptance`、`status`、`operation_id`、`document_id`、`decided_at`。三分支必须按“字段存在/字段完全省略”严格校验：

| 分支 | 必须字段 | 必须完全省略字段 |
|---|---|---|
| `ACCEPTED` | `task_id`，32 位小写十六进制 | `rejection_code`、`stored_event_hash`、`incoming_event_hash` |
| `REJECTED` | `rejection_code` | `task_id`、`stored_event_hash`、`incoming_event_hash` |
| `CONFLICT` | `stored_event_hash`、`incoming_event_hash`，均为 64 位小写十六进制 | `task_id`、`rejection_code` |

`REJECTED` 的 V1 `rejection_code` 允许值为 `DOCUMENT_ID_ALREADY_REGISTERED`、`INGRESS_FROZEN`、`CURRENT_GENERATION_UNAVAILABLE`。同一操作不同 payload 必须映射为 `CONFLICT`，不能降格成普通拒绝。任何禁止字段即使值为 `null` 也属于出现，必须拒绝。

使用相同 Topic 和 `MessageGroup=operation_id` 只提供同组有序传输条件；Python 还必须先在持久事务中写 acceptance Outbox，再允许同一操作写最终结果 Outbox，Sender 按持久顺序发送，才能证明 acceptance 先于最终结果。

**当前证据状态**：该 acceptance 是目标合同。当前 Python 尚无对应严格模型、Outbox 写入和测试，状态为 `NOT_IMPLEMENTED / NOT_RUN`。V0.1.0 只设计 Schema 和样本，不得声称 Python 已经发送或 Java 已经消费该事件。依据为 `LLD-003-RAG预留对接合同.md` 第 5 节对当前源码缺口的核对。

### 2.3 冻结 RAG → Java 最终结果合同

| 项目 | 固定值/规则 |
|---|---|
| Topic | `card_rag_document_result` |
| Tag | `document_ingestion_result` |
| Key | `operation_id` |
| MessageGroup | `operation_id` |
| Body | UTF-8 JSON，`schema_version=1.0` |
| Java Consumer Group | `java_file_center_rag_result_cg`，本项目新增资源，后续创建 |

最终 `document_ingestion_result` 只区分 `READY` 和 `FAILED`，不承担接纳拒绝/冲突语义。`READY` 要求索引批次/代标识存在并省略失败字段；`FAILED` 要求失败代码/阶段存在，并按 Schema 约束索引字段。JSON 键“省略”和值为 `null` 不得视为同一语义。

### 2.4 冻结文件引用合同

- 本地兼容格式：`file_ref=local-file-ref:v1:<reference_id>`；
- MinIO Object Key 直接等于 `reference_id`；
- `reference_id` 非空，不包含 `/`、`\\`，且不能为 `.` 或 `..`；
- 对象用户元数据包含 `file_name` 和 `media_type`；
- Java 上传时对原始字节流计算 `expected_content_sha256`，格式为 64 位小写十六进制；
- MinIO ETag 单独记录，不得替代 SHA-256；
- MQ Body 不携带 Bucket、Object Key、预签名 URL、AccessKey 或 SecretKey。

该 `local-file-ref` 是本地联调合同。生产文件取得方式需在未来安全设计中重新裁决，但稳定的 `document_id`、`operation_id` 和内容哈希语义应保持。

### 2.5 冻结 Java → RAG 逻辑文件事实变更合同

| 项目 | 固定值/规则 |
|---|---|
| Topic | `card_rag_doc_intake` |
| Topic 类型 | FIFO |
| Tag | `file_fact_changed` |
| Key | 恰好一个，等于 Body `operation_id` |
| MessageGroup | 等于 Body `file_id` |
| Property `payload_hash` | 按 LLD-003 第 7 节规范化 Body 后，对 UTF-8 字节计算 SHA-256 小写十六进制 |
| Body | UTF-8 严格 JSON Object，`schema_version=1.0`、`event_type=file_fact_changed` |
| 当前状态 | `CONTRACT_ONLY / NOT_SENT / NOT_RUN` |

`change_type` 只允许：`CREATED`、`CONTENT_REPLACED`、`METADATA_UPDATED`、`ENABLED`、`DISABLED`、`DELETE_REQUESTED`、`DELETED`、`FAILED`。公共事实包含 `operation_id/file_id/file_version/lifecycle_status/availability_status/original_name/display_name/changed_at`；`file_version` 取对应已提交文件事实的正整数 `row_version`，对同一 `file_id` 单调增加，允许因内部状态事务出现间隔。

可读内容分支必须包含 `document_id/file_ref/media_type/size_bytes/content_sha256`。`CONTENT_REPLACED` 还必须包含不同于新 `document_id` 的 `previous_document_id`；`CREATED` 和其他分支必须省略该字段。`DELETE_REQUESTED/DELETED/FAILED` 不携带可读 `file_ref`；`DELETED` 仍携带最后的 `document_id`，使 RAG 能精确退役旧文档。

`file_fact_changed.operation_id` 只标识一份已提交、不可变的事件 payload。Java 文件命令使用的内部 `file_workflow_id` 关联一次业务流程；涉及 PostgreSQL/MinIO 创建、替换或删除时，它可以跨 TX1、事务外对象操作和 TX2 复用，以便补偿与对账。它与 MQ `operation_id` 属于不同命名空间。每个文件事实提交点必须生成独立的事件 `operation_id`，不得把一个内部流程 ID 填入两份不同 payload。删除请求和删除完成因此必须使用不同的事件 `operation_id`。

RAG 后续按 `operation_id` 和规范 payload hash 幂等，按 `file_id` 保存最后应用的 `file_version`：低版本作为陈旧消息记录并忽略，同版本同 payload 作为重复 ACK，同版本不同 payload 标记冲突，高版本才应用。`CONTENT_REPLACED` 必须在 RAG 自己的事务边界内使旧 `previous_document_id` 退出可用集合并处理新 `document_id`，不能让两个版本同时作为当前文档。

### 2.6 冻结未来 Transactional Outbox 原子边界

当 MQ 进入后续版本范围时，产生已提交文件事实的 PostgreSQL 本地事务必须同时写入：

1. `file_record` 当前事实及必要状态历史；
2. 对应 RAG delivery operation；
3. 完整、不可变的 Outbox UTF-8 JSON 与规范 payload hash。

创建 ACTIVE、替换切换、元数据修改、启停、删除请求、删除完成和失败转换分别生成对应 `file_fact_changed`。Sender 只能在事务提交后发送；发送失败重试必须复用 Outbox 中已冻结的 `operation_id/file_version/payload`，禁止重新查询后来版本的文件行来重建旧事件。PostgreSQL、MinIO 和 RocketMQ 仍不是一个 ACID 事务：MinIO 操作继续由状态机和补偿收敛，MQ 只对已经提交的数据库事实采用 Transactional Outbox。

V0.1.0 只把上述规则写入 ADR、LLD、Schema 和固定样例，不创建 operation/Outbox/Inbox 表，不引入 Producer/Consumer，不初始化 Topic/Group，不增加 MQ 运行配置。

### 2.7 V0.1.0 交付物

- 入库消息 JSON Schema；
- `file_fact_changed` 八种变更的 JSON Schema、正向分支样例和反向条件样例；
- `document_ingestion_acceptance` 的 `ACCEPTED/REJECTED/CONFLICT` JSON Schema 与正反例；
- READY/FAILED 结果 JSON Schema；
- 每个有效分支的固定 JSON 样本；
- 缺字段、额外字段、非法哈希、错误状态分支和 `null`/省略差异的无效样本；
- Java 序列化/反序列化契约测试设计；
- Schema 与样本 SHA-256 清单，防止无版本漂移。

## 3. V0.1.0 明确不做

- 不引入 `rocketmq-client-java` 运行 Bean；
- 不创建 Producer/Consumer，不初始化 Topic/Group；
- 不启动 RocketMQ、Python RAG、Milvus 或 Elasticsearch；
- 不创建 RAG 操作表、Outbox 表、acceptance/result 消费幂等表；
- 不返回固定的“RAG 成功”以模拟真实处理；
- 不把静态契约测试称为联调、消息闭环或端到端 PASS。

`rocketmq-client-java:5.0.5`、RocketMQ Server/Proxy `5.1.4` 和 Python Client `5.1.1` 仍作为目标架构合同版本冻结；它们不是 V0.1.0 的运行依赖。

## 4. 原因

- 文件管理可以独立形成可验证的业务闭环，RAG 运行时不是其必要依赖。
- 先固定对象键、元数据和 SHA-256，避免后续接入时重新迁移全部文件。
- 先固定严格 Schema 和样本，能够在没有中间件时发现大部分字段漂移。
- 以稳定 `file_id` 分组和单调 `file_version` 应用，才能覆盖同一逻辑文件的替换、启停和删除；只按会变化的 `document_id` 分组会丢失跨版本顺序。
- 把文件事实和不可变 Outbox 放在同一 PostgreSQL 事务，才能防止“数据库已提交但事件永久丢失”以及“重试时用新快照伪造旧事件”。
- 延迟 MQ Adapter、Outbox 和结果消费，防止第一期出现未验收的半条分布式链路。

这些理由是阶段划分判断，不代表 RAG 集成本身不重要，也不代表契约测试等于运行测试。

## 5. 后果

### 5.1 正向结果

- V0.1.0 的启动和故障面只包含 Java、PostgreSQL、MinIO。
- 文件对象从第一天就兼容后续本地 RAG 读取约束。
- Java/Python 团队可以围绕同一 Schema 和样本评审，无需共享 Java JAR。

### 5.2 代价与风险

- 没有验证 RocketMQ 顺序、重投、ACK、DLQ 和 Proxy 网络行为。
- 没有验证 Java MinIO SDK 写入后 Python SDK 能按预期读取元数据和内容。
- 当前 Python 尚未实现 acceptance 模型与 Outbox；静态目标 Schema 不证明真实 Python 能生成该事件。
- 当前 Python 尚未实现 `file_fact_changed` 消费、按 `file_version` 防陈旧覆盖或替换旧文档的行为；Schema 通过不证明这些行为存在。
- 参考 RAG 实现变化可能使已冻结合同失效，因此接入前必须重新核对目标 RAG 的 HEAD、锁文件和相关文件哈希。
- 未来仍需新增 Outbox、结果幂等、对账和状态模型，当前契约不能替代这些实现。

## 6. 进入真实接入阶段的门禁

1. 固定 Java 和 Python 的代码对象、依赖锁与契约文件哈希。
2. Python 实现并验证 `file_fact_changed` 严格模型、按 `file_id/file_version` 幂等应用和替换退役；同时实现 acceptance 严格模型和同账本事务 Outbox。用双方真实模型交叉验证固定样本。
3. 初始化并读回两个 Topic、双方 Consumer Group 和 FIFO 属性。
4. 验证 Java MinIO SDK 8.5.17 写入、Python MinIO SDK 7.1.15 读取、元数据与 SHA-256 一致。
5. 实现 Java 文件事实/RAG delivery operation/不可变 Outbox 同 PostgreSQL 事务、提交后发送，及 Python 持久接纳后 ACK、结果 Outbox 和 Java 消费幂等。
6. 执行 Java → MQ → Python acceptance → MinIO/RAG 处理 → Python final result → MQ → Java 完整业务链，并保存 message id、operation id、接纳状态、数据库状态与最终 ACK 证据。

只有同一冻结对象上的第 1～6 项完成后，才可以表述“RAG 真实接入通过”。

## 7. 被否决方案

### 7.1 V0.1.0 同时完成文件管理和 RAG 全链路

否决原因：超出用户明确的一期范围，并把文件存储故障与 MQ/Python/索引故障同时引入，无法形成清晰的阶段证据。

### 7.2 用 Mock RAG 返回成功作为接入证明

否决原因：只能证明 Java 调用了 Mock，不能证明真实 Schema、RocketMQ、MinIO 跨 SDK 或 Python 处理行为。

### 7.3 MQ 直接携带文件字节或预签名 URL

否决原因：扩大消息体，泄露存储拓扑/临时凭据，并弱化稳定文件身份和内容完整性验证。
